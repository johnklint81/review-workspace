# Backup and Restore

## Purpose

Review Workspace provides a project-scoped backup of the review application's data.

The current project is the **C. elegans review**.

The backup is intended to provide a portable copy of the application's review data that can be restored into another compatible PostgreSQL/Supabase environment.

## Backup scope

The backup currently contains these application tables:

- `projects`
- `project_members`
- `articles`
- `article_assignments`
- `screening_decisions`
- `conflict_messages`
- `conflict_resolutions`

The backup includes project membership roles, including the project administrator role.

## Excluded data

The application backup deliberately does not contain:

- Supabase Auth users and credentials
- Passwords
- Authentication tokens
- Supabase platform/system tables
- Storage objects outside the `review-backups` bucket
- Other projects

This is an **application-data backup**, not a complete Supabase platform disaster-recovery backup.

## Creating a backup

A project administrator can create a backup from:

**Review Workspace -> Administration -> Create backup**

The backup is generated by the `create-review-backup` Supabase Edge Function.

The Edge Function:

1. Verifies the authenticated user.
2. Verifies membership in the requested project.
3. Requires the user's project role to be `admin`.
4. Reads the seven application tables for that project.
5. Creates a JSON backup.
6. Stores the backup in the private `review-backups` Storage bucket.
7. Creates a temporary signed download URL.

Privileged Supabase credentials remain server-side and are never sent to the Flutter Web application.

## Backup file format

The backup is JSON.

A backup contains:

```text
backup_version
application
project
exported_at
exported_by
tables
excluded_from_this_backup
```

The `tables` object contains one array for each application table.

## Local restore test

The restore procedure has been tested against a clean local Supabase environment.

### Requirements

- Docker
- Supabase CLI
- PostgreSQL client (`psql`)
- A compatible copy of the Review Workspace repository
- A Review Workspace JSON backup

### Start the local Supabase environment

From the project root:

```bash
npx supabase start
```

The local database used for testing was:

```text
postgresql://postgres:postgres@127.0.0.1:54322/postgres
```

### Reset the local database

To start from a clean database:

```bash
npx supabase db reset
```

This applies the repository migrations and affects only the local Supabase environment.

### Local Auth dependency

The application backup does not contain Supabase Auth users, but `project_members.user_id` references `auth.users.id`.

For the local restore test, local placeholder Auth users with the same UUIDs as the project members were created.

These are dummy local users only. Do not copy production passwords, authentication tokens, or credentials into the local restore environment.

Example local test emails:

```text
john@example.local
greger@example.local
adams@example.local
```

### Restore workflow

The tested restore workflow converts the JSON backup into SQL statements for the local database.

The restore must insert data in dependency order:

```text
auth users
    |
    v
projects
    |
    v
project_members
    |
    v
articles
    |
    v
article_assignments
    |
    v
screening_decisions
    |
    v
conflict_messages
    |
    v
conflict_resolutions
```

### Restore

Apply the generated SQL to the local database:

```bash
psql "postgresql://postgres:postgres@127.0.0.1:54322/postgres"   -f /tmp/restore_review_backup.sql
```

A failed transaction should roll back rather than leaving a partially restored database.

## Restore verification

After restoring, verify the project and member count:

```bash
psql "postgresql://postgres:postgres@127.0.0.1:54322/postgres"   -c "SELECT p.title, count(pm.user_id) AS members
      FROM public.projects p
      LEFT JOIN public.project_members pm
        ON pm.project_id = p.id
      GROUP BY p.id, p.title;"
```

Expected result for the tested backup:

```text
C. elegans review | 3
```

Verify all seven application tables:

```bash
psql "postgresql://postgres:postgres@127.0.0.1:54322/postgres"   -c "SELECT 'projects' AS table_name, count(*) FROM public.projects
      UNION ALL
      SELECT 'project_members', count(*) FROM public.project_members
      UNION ALL
      SELECT 'articles', count(*) FROM public.articles
      UNION ALL
      SELECT 'article_assignments', count(*) FROM public.article_assignments
      UNION ALL
      SELECT 'screening_decisions', count(*) FROM public.screening_decisions
      UNION ALL
      SELECT 'conflict_messages', count(*) FROM public.conflict_messages
      UNION ALL
      SELECT 'conflict_resolutions', count(*) FROM public.conflict_resolutions
      ORDER BY table_name;"
```

For the tested backup, the verified counts were:

```text
projects                 1
project_members          3
articles                 0
article_assignments      0
screening_decisions      0
conflict_messages        0
conflict_resolutions     0
```

The restored project was `C. elegans review`, with three project members.

## Production safety

Never run the local restore commands against the production Supabase database.

The local development database uses:

```text
127.0.0.1:54322
```

The hosted production database is a separate environment.

Before any production restore is considered, the restore process should be reviewed carefully and a dedicated staging environment should be used first.

## Backup retention

Downloaded backup files may contain research data once screening begins.

Keep backups:

- outside the Git repository
- outside public web storage
- protected from unauthorized access
- under an appropriate retention policy for the research project

Do not commit backup JSON files to GitHub.
